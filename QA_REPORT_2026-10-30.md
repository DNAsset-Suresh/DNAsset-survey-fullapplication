## 2. Initial inspection and corrections

The existing stack is vanilla HTML/CSS/JavaScript modules, Express 5 on Node.js 24, PostgreSQL through PGlite or `pg`, optional Supabase clients, private filesystem/Supabase storage, PDFKit, pdf-parse, SheetJS, Tesseract and Nodemailer. Tests use the existing Node test runner and Supertest.

The initial configuration selected the cloud database, but its certificate chain could not be verified. The user explicitly selected the saved local database instead. `USE_LOCAL_DB=true` now takes precedence over `DATABASE_URL`; TLS verification remains enabled for cloud mode.

Confirmed problems corrected:

- Startup attempted to execute a destructive Green Valley deletion migration containing an invalid column reference. Migration 008 is retired and does nothing.
- Startup reset demo passwords, changed profiles and removed accounts. Those startup actions and the universal-password fallback were removed. Existing credentials are checked against stored accounts; successful local logins upgrade legacy password storage to scrypt.
- The local adapter ignored the acting user on reads. Reads now execute in an authenticated database transaction with the user's identity and PostgreSQL row-level security.
- Sessions used an embedded signing secret and logout did not revoke them. Local sessions now use random tokens, one-hour access expiry, rotating refresh tokens, logout revocation and password-change revocation. Restarting the server requires signing in again.
- Public storage URLs bypassed authentication and resolved the wrong directory. File access now requires authorization before issuing a random 60-second capability; paths are confined to storage, deleted metadata invalidates links, and missing files return readable JSON 404 responses. PDF/image previews use inline delivery; downloads use attachment delivery.
- Project-password unlock granted membership automatically. Unlock now requires an existing assignment and is bound to the authenticated session. Resource routes consistently check project protection. Password values are omitted from API responses.
- Upload history was inserted separately from the file transaction and cascaded away on replacement/deletion. A database trigger records history atomically. Original upload IDs and project/property/category references survive file removal.
- Upload requests waited for extraction and email. Uploads now acknowledge saved bytes and metadata before processing. A serialized queue loads files from durable storage; analysis runs in a bounded child process, with a 45-second deadline and a 256 MiB JavaScript heap limit. Interrupted jobs resume on startup. Native PDF/canvas teardown crashed Windows worker threads during testing; child-process isolation resolved that regression.
- PDF parsers were not destroyed. They now release resources. Extraction no longer treats arbitrary dates, serial-number columns or checklist location fields as source-document facts. Image OCR results require manual review.
- The matrix and document library repeatedly loaded individual checklists. Shared queries now batch documents/files/progress. Documents and Verification display up to 25 surveys per page; upload history is paginated and can be scoped to a project. Duplicate initial requests and an unnecessary project-detail request were removed.
- Static inline styles violated the existing content-security policy. They were moved to CSS. Mobile action-button/top-bar overflow was fixed. Settings now reads actual account records, and global survey creation asks the user to select a project.
- An unauthenticated analysis-export link was replaced with an authenticated download. Expired sessions return to sign-in. Archived project mutation controls are disabled.
- Embedded credentials were removed from maintenance scripts. Previously embedded external credentials were not rotated; rotation remains an administrator follow-up.

### Restore procedure

Keep the application stopped during restoration. Preserve a fresh copy of the current snapshot and storage before any rollback. Do not overwrite the verified backup or the current database merely to inspect old records.

To inspect or operate the backup, copy its `survey_db.tar.gz` and `storage` folder into a **new, separate restoration directory**. Set `USE_LOCAL_DB=true`, `LOCAL_DATABASE_FILE` to that copied snapshot, and `LOCAL_STORAGE_DIRECTORY` to that copied storage folder. Keep `EMAIL_NOTIFICATIONS_ENABLED=false` and `STORAGE_CLEANUP_ENABLED=false` during validation, then start the app. This restores the pre-replacement workspace without destroying pondy in the current snapshot. Never point the application directly at the only backup copy, because initialization may apply safe schema upgrades.

An administrator can also reverse just the archive by clearing Green Valley's `archived_at` field after taking a current backup; that does not require deleting pondy. The backup restore was exercised in an isolated database, not over the active dataset.
